# ADR-8：模型统一走云端，LLM 与 Embedding 配置必须分离

> 状态：**已实现**（M2 embedding + M3 LLM 生成 + M6 reranker；三项配置独立成块）
> 实现落点：`apps/api/core/config.py`（`LLM_*` / `EMBED_*` / `RERANK_*` 三块）、`agent/provider/{embedding,rerank}.py`
> 服务商：DeepSeek（LLM）· 通义千问 text-embedding（1024 维）· **qwen3.7-text-rerank**（精排）

## 背景

模型部署方式影响的不只是成本，还影响**评测能不能归因**。

**本地小模型（7B 级）的输出质量会掩盖检索层的问题**：评测时无法区分"检索没召回"和"模型没用好召回的内容"，§14 的归因价值直接失效。

另一个隐患藏在配置里：**LLM 与 Embedding 的影响面完全不同**——LLM 只影响生成（可随时改），Embedding 影响**整个向量库**（不同模型的向量空间不兼容，变更后必须全量重嵌入）。v1 的指南里写着"切换模式不影响已入库数据"，**这句话只对 LLM 成立**。

## 决策

全程使用云端模型，不部署本地模型；**LLM / Embedding / Reranker 三项配置独立成块**，互不干扰。

## 替代方案

| 方案 | 放弃理由 |
|------|---------|
| 本地 Ollama（v1 的做法） | 需 GPU 或大内存；小模型输出质量会掩盖检索层问题、破坏归因 |
| 云端 + 本地双模式并存 | 配置组合与测试矩阵翻倍，而本地模式在本项目没有必须存在的场景 |
| 多服务商自动路由 | 增加鉴权/限流/降级复杂度，MVP 无收益 |

## 与设计文档的差异（按实际实现修正）

| 设计文档写的 | 实际做法 | 原因 |
|-------------|---------|------|
| Reranker = `bge-reranker-v2-m3` | **`qwen3.7-text-rerank`**（DashScope **原生** text-rerank 端点，非 OpenAI 兼容） | 实际可用模型以服务商为准；端点形态不同（`output.results[].relevance_score`），因此单独封装 `agent/provider/rerank.py` 而非复用 OpenAI 客户端 |
| "`EMBED_MODEL` 或 `EMBED_DIM` 变更时启动自检直接拒绝启动" | **只实现了维度运行时校验**：首次成功响应即比对 `len(vector) == EMBED_DIM`，不一致立即失败 | 未做"模型名指纹入库 + 启动拒绝"（需要额外的元数据表与启动校验逻辑）。当前防的是"维度漂移"（最致命的静默损坏），防不了"同维度换模型"（如 1024 维换另一个 1024 维模型） |
| Reranker 阈值按模型标定 | 落地为**不设绝对阈值**：精排分只用于**排序**，不做"相关性阈值过滤" | §8.4 的引用相关性阈值依赖 reranker 分数的绝对值；M6 只用到排序（`RERANK_TOP_N=6`），阈值过滤未实现 → 换模型不会导致阈值失效（因为还没有阈值） |

## 代价与局限（必须承认）

1. **完全依赖网络与第三方可用性**——服务商抖动即影响服务。**这不是理论风险，本项目的验收过程实测撞上过两次**：LLM 账号余额不足（429）、Reranker 免费额度耗尽（403 `AllocationQuota.FreeTierOnly`）。两次都由降级矩阵接住（§8.3），用户侧零中断。
2. **成本随用量线性增长**——靠配额与成本监控控制；当前**没有成本聚合与告警**（设计文档 §5.2 的日成本监控未实现），`messages.token_usage` 有原始数据但没有汇总作业。
3. **用户数据需发送至第三方**——云端方案的固有代价。PII 脱敏（ADR-6）降低暴露面但不能消除。
4. **Reranker 的网络往返进关键路径**：M7 实测精排中位 176–261ms，使检索段 P95 从 251ms 升到 463ms，**超出 §8.2 的 300ms 预算**。已按 §8.3 用 800ms 超时兜住（超时即降级为 RRF 顺序）。

## 影响

- 三项配置分离让"换 LLM 不影响向量库"成为可执行的约定（改 `LLM_*` 无副作用）。
- 云端依赖 + 明确承认的代价，直接催生了 M6 的降级矩阵——**降级不是补丁，是这种架构的必需品**。
