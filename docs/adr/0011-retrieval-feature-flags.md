# ADR-11：检索链路的 feature flag（配置文件 + Redis 覆写）

> 状态：**已实现**（M6 落地，M7 用于五管线对比）
> 实现落点：`agent/retrieval/flags.py`、`apps/api/api/v1/meta.py`（`GET/POST /api/v1/flags`）
> 这是**实现期新增**的 ADR

## 背景

对比评测要求"同一批 query、不同管线、一次跑完"。最朴素的做法是**改代码 → 重启 → 重跑评测**，但它有三个致命问题：

1. **不可复现**：串行改代码意味着两次运行之间代码可能还有其他改动；
2. **慢**：每条管线都要一次完整重启 + 全量重跑；
3. **降级验收需要"制造故障"**——总不能在真故障里做验收（也不该为了验收去拔网线）。

设计文档 §14.3 给了方向：轻量 flag（配置文件 + Redis 覆写，无需引入 Unleash）。

## 决策

两级来源，**覆写优先**：

| 来源 | 用途 | 形态 |
|------|------|------|
| 配置文件（`.env` → `settings.retrieval_*`） | **生产默认值** | 混合检索与精排默认开启 |
| Redis 覆写（`flag:{name}`） | 运行时切换（评测 / 故障演练） | `POST /api/v1/flags`，**仅 dev 环境**，变更落 `audit_logs` |

四个 flag：`retrieval.hybrid.enabled`、`retrieval.rerank.enabled`、`retrieval.vector.enabled`、`retrieval.keyword.enabled`。

配套：**5 秒进程内缓存**（检索在热路径上，每次查询都读 8 个 Redis key 属读放大；5s 陈旧窗口对评测切换与故障演练完全够用）。

## 替代方案

| 方案 | 放弃理由 |
|------|---------|
| Unleash / Flagr 等专业方案 | 多一个有状态服务 + 一套 UI，个人项目收益不成比例 |
| 只改 `.env` + 重启容器 | 就是"慢且不可复现"的原始方案；且评测要跑 5 条管线就重启 5 次 |
| 把 flag 做成请求参数 | 语义错位（这是**运维/评测开关**，不是用户输入）；也会让"用户能关掉检索"成为可能 |
| 进程内全局变量开关 | 多副本不一致（API 进程可能多于一个），评测结果不可复现 |

## 代价与局限

1. **写接口只在 dev 开放**（`app_env != "dev"` → 403）：flag 是**全局**开关，开放给普通用户等于给所有人关掉检索能力。生产变更走配置或运维通道。
2. **5s 缓存带来"切换后不是立即生效"**：评测脚本每条管线切换后需等一拍（脚本内已按管线顺序执行，天然满足）。
3. **flag 组合爆炸的隐患**：4 个布尔量 = 16 种组合，其中"两条召回都关"是无效组合（等于没有检索）。当前靠代码里的 `if not vector_rows and not keyword_rows: degraded.append("retrieval")` 兜住语义，但没有 flag 组合的合法性校验。

## 影响

- **M7 验收 H1 直接受益**：`evals/compare_pipelines.py` 一条命令跑五条管线（含两条故障态），无需改代码或重启。
- **M6 验收 G2/G3 用同一开关模拟依赖故障**，不依赖真实故障注入（§8.3 的验收方式）。
- **一次意外的真实故障演练**：M6 评测中途 DashScope 免费额度耗尽（403），精排 100% 降级——因为降级链路本来就被 flag 演练过，系统行为完全符合预期（用户零中断 + 角标如实显示）。
