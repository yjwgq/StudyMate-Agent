# ADR-12：ReAct 决策记忆化（保证重放一致与"批准什么就执行什么"）

> 状态：**已实现**（M5 落地）
> 实现落点：`agent/graph/react.py::_complete_with_memo`（Redis，key = `react_decision:` + sha256，TTL 1h）
> 这是**实现期新增**的 ADR —— 它源自一个真实的、看起来像"审批功能坏了"的 bug

## 背景

M5 的 HITL 链路是：工具命中 L2 → 落 `approvals`（pending）→ `interrupt()` 暂停图 → 人工决策 → `Command(resume=…)` 从 checkpoint **续跑**。

问题出在 LangGraph 的恢复语义：**恢复时会从现在这个节点的最开头重新执行**（`interrupt()` 的调用点会返回 resume 值，但节点里 `interrupt()` **之前**的代码会重跑一遍）。

而 `interrupt()` 之前恰好有一次 **LLM 调用**（ReAct 决策：要不要调工具、用什么参数）。于是：

1. LLM 被再调一次 → `temperature=0.3` 下**可能产出参数不同的工具调用**；
2. 参数不同 → 严格匹配找不到"已批准的那条审批" → **再次暂停**（表现：批准后还是"待审批"，像死循环）；
3. 更危险的是第 3 种可能：如果为了绕过 2 而放宽匹配，就会变成**"批准的是 A 参数，实际执行 B 参数"**——这是审批语义上的安全漏洞。

## 决策

**对 ReAct 决策做记忆化**：以 `(conversation_id, step_id, round, 完整消息列表, 工具名列表)` 的哈希为 key，把该轮 LLM 的决策（文本 + `tool_calls` + usage）缓存进 Redis（TTL 1h）。节点重跑时**命中同一决策**，参数逐字节一致。

于是：

- 重放/重跑拿到**完全相同的工具调用** → 能精确匹配到已批准的审批 → 继续执行；
- 审批语义严格化：**批准什么就执行什么**；
- 重跑不再浪费第二次 LLM 调用（顺带省钱）。

## 替代方案

| 方案 | 放弃理由 |
|------|---------|
| `temperature=0` 让它"自然一致" | 不保证。多家服务商在 temp=0 下仍有非确定性（浮点/批处理/版本），把安全语义押在"模型恰好一致"上不可接受 |
| 用宽松匹配（工具名 + 线程）找审批 | 会执行"和批准内容不同"的参数——审批变成橡皮图章，是不可接受的安全退化 |
| 把审批判断移到 LLM 之前 | 需要把"这个工具调用会不会命中 L2"提前算出来，而参数本身就是 LLM 产出的，逻辑上绕不开 |
| 把决策存进 LangGraph state | state 会被 checkpoint 序列化；存 LLM 的完整响应（含 usage/工具调用对象）会让 checkpoint 体积与反序列化复杂度上升（M5 已遇到 `Step` / `UUID` 类型的反序列化告警） |

## 代价与局限

1. **Redis 不可用时退化为直接调用**（不阻断主流程）——此时重跑一致性回到"靠运气"，但至少不会坏掉功能。这是 fail-open 的取舍，已明确记录。
2. **缓存 key 含完整消息列表**：多轮长对话的 key 计算有成本（JSON 序列化 + sha256），但相比一次 LLM 调用（数百毫秒）可忽略。
3. **TTL 1h 与审批有效期 1h 耦合**：超时后重跑会重新决策（此时审批通常也已 `expired`，语义一致）。
4. **只覆盖 ReAct 决策**：`planner` 与 `synthesize` 的重跑没有记忆化（前者在 interrupt 之前不会重跑，后者不在审批路径上）。

## 影响

- 修复了"批准后仍待审批"的表象 bug，同时把审批语义从"大概执行了批准的东西"收紧为"**逐字节执行批准的东西**"。
- 这条 ADR 的取材本身说明一个工程习惯：**当"功能没坏但行为诡异"时，先怀疑框架的恢复语义，再怀疑自己的代码**。
