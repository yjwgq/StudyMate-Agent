# 检索层评测报告

> 交付物：独立评测报告（设计文档 §20 列为 P0）
> 数据来源：`evals/reports/*.json`（本报告的每个数字都能在仓库里找到原始文件）
> 版本：v1.0（2026-09-24）｜评测对象：M6 之后的完整检索链路

## 1. 方法论

### 1.1 为什么是**检索层**指标

"效果变好"必须能回答一个问题：**是召回变好了，还是排序变好了？** 答案层指标（RAGAS 那一类）只能告诉你答案好不好，回答不了这个归因问题；而且它由 LLM judge 产生，本身带随机性。

因此本项目自建检索层指标，**全部是确定性计算**：

| 指标 | 定义 | 关注点 |
|------|------|--------|
| Recall@k | 应命中文档（rel≥1）出现在 top-k 的比例 | 召回能力 |
| MRR@k | 首个相关结果的倒数排名 | **首条命中质量** |
| nDCG@k | 分级折损（rel ∈ {0,1,2}，`2^rel−1` 加权） | **整体排序质量** |

判分粒度是**文档级**：检索返回父块 → 归并到文档 → 与 golden 的 `expected_docs` 比对（同一文档的多个父块按首次出现计）。

### 1.2 golden set 的两代

| 版本 | 规模 | 语料 | 特点 |
|------|------|------|------|
| `golden_v1.jsonl` | 50 条 | 10 篇**合成锚点文档** | 每篇埋唯一事实锚点，`expected_docs` 可静态推导（标注零歧义，代价是**区分度低**） |
| `golden_v2.jsonl` | **68 条** | 13 篇 = 10 篇合成 + **3 篇真实技术文档** | v1 的 50 条（跨文档分级修正）+ 18 条**人工出题标注**的真实语料题 |

真实语料 = 仓库内**为人撰写**的技术文档快照（README / M6 验收手册 / 设计文档第 8 章），可一键重建（`build_golden_v2.py --write-corpus`）。题型分布：专名精查 4 / 语义改写 5 / 跨文档 4 / 长尾 3 / 数字 2。

### 1.3 噪声地板（先量误差，再谈改进）

同一份代码、同一批样本、重复 5 次：

| 指标 | mean | σ | 门禁阈值（2σ） |
|------|------|---|---------------|
| Recall@10 | 1.0000 | **0.0** | 0.0 |
| MRR@10 | 1.0000 | **0.0** | 0.0 |
| nDCG@10 | 0.9978 | **0.0** | 0.0 |

**结论：检索层指标是确定性的（σ=0）**——这不是"不用做噪声地板"，而是更强的结论：检索层指标可以做**精确阈值门禁**，不需要 2σ 松弛。
（原始数据：`evals/reports/noise_floor_m3.json`）

> 反面对照：设计文档要求把 RAGAS 类指标的噪声地板用于门禁，因为 LLM judge 有随机性。**本项目未引入答案层指标**，所以那部分噪声地板是空缺——不虚构。

### 1.4 怎么跑

```bash
# 五条管线一条命令跑完（flag 驱动，无需改代码/重启）
uv run python -m evals.compare_pipelines --base-url http://127.0.0.1:8080 --k 10 \

```

## 2. 结果

### 2.1 主对比表（golden_v2，68 条，k=10，2026-09-24）

| 管线 | Recall@10 | MRR@10 | nDCG@10 | P50 | P95 |
|------|-----------|--------|---------|-----|-----|
| ① 单路向量（**M3 基线在新集重跑**） | 1.0000 | 0.9240 | 0.9497 | 165ms | 207ms |
| ② + 混合检索（关键词 + RRF） | 1.0000 | 0.9387 | **0.9567** | 157ms | 185ms |
| ③ + Rerank（精排真实生效） | 1.0000 | **0.9485** | 0.9554 | 416ms | 463ms |
| ④ 单路向量 + **向量路故障** | **0.0000** | 0.0000 | 0.0000 | 151ms | 183ms |
| ⑤ 混合 + 向量路故障（关键词兜底） | 0.9926 | 0.9485 | 0.9514 | 344ms | 396ms |

（原始数据：`evals/reports/m7_compare.json`、`m7_scores.json`）

### 2.2 逐项归因（**这张表的灵魂**）

| 改动 | 指标增量 | 来源 |
|------|---------|------|
| **+ 混合检索（关键词 + RRF）** | nDCG **+0.0070**、MRR **+0.0147** | ② − ① |
| **+ Rerank** | MRR **+0.0098**、nDCG **−0.0013** | ③ − ② |
| **依赖故障可用性**（混合 vs 单路） | Recall **+0.9926** | ⑤ − ④ |

**读法**：

- 混合检索的增益方向一致（两个指标都为正）：关键词路补上了向量路"语义相近但用词不同"之外的另一半能力——**专名与术语的精确匹配**。
- 精排的增益**方向不一致**（MRR 涨、nDCG 微跌）：它更擅长把正确文档提到最前，而在少数多文档排序上与人类偏好有分歧。**68 条样本下这个量级（0.0098 / 0.0013）接近噪声，不宜过度解读**。
- 依赖故障可用性是最干净的一组对照：两者都在向量路不可用时运行，唯一差别是有没有关键词路 → **0.0000 vs 0.9926**。

### 2.3 延迟（如实记录，含超预算项）

| 阶段 | 目标（设计文档 §8.2） | 实测 |
|------|---------------------|------|
| 检索段（不含 query embedding） | P95 < 300ms | ① 207ms · ② 185ms · **③ 463ms（超预算）** |
| 热态拆解（②） | — | 向量路 1–3ms、关键词路 3–4ms（真并行）、精排 176–261ms |

**精排是超预算的唯一原因**：DashScope rerank 的网络往返进关键路径。已按 §8.3 用 800ms 超时兜住（超时即降级为 RRF 顺序 + UI 角标）。
未做的优化（记录备查）：候选从 50 收敛到 20；精排结果进程内缓存。

## 3. 评测过程中发现的两个缺陷（方法论价值 > 数字本身）

### 3.1 合成语料导致**指标饱和**（M6 发现）

M3 的 10 篇合成文档主题彼此独立，结果：

| | Recall@10 | MRR@10 | nDCG@10 |
|---|---|---|---|
| 单路向量 | 1.0000 | 1.0000 | 0.9978 |
| + 混合检索 | 1.0000 | 1.0000 | 0.9978 |
| + Rerank | 1.0000 | 1.0000 | 0.9978 |

**三条管线完全一样**。这不是"系统已经完美"，而是**评测集没有区分度**——此时任何"提升 Y 个点"的说法都不成立。
→ M7 引入真实文档后，单路基线从 MRR 1.0000 降到 0.9240，改进空间才显现出来。

### 3.2 跨文档问的 rel 分级是**任意约定**（M6 发现，M7 修正）

v1 对"A 和 B 分别是什么"采用"查询里第一个术语所在文档记 rel=2、第二个记 rel=1"。但该查询对 A、B **同等权重**：

| query | ② RRF 顺序 | ③ 精排顺序 | nDCG 变化 |
|-------|-----------|-----------|----------|
| q046「监督学习和TCP 三次握手分别是什么」 | computer_networks → ml_basics | **ml_basics → computer_networks** | 0.8918 → **1.0**（修好） |
| q047「对比事务 ACID 与 CAP 定理」 | db_systems → distributed_systems | distributed_systems → db_systems | 1.0 → 0.8918（变差） |
| q050「单元测试、RAG 的定义和区别」 | software_engineering → rag_notes | rag_notes → software_engineering | 1.0 → 0.8918（变差） |

精排在语义上做对了（q046 是真实修复），而 q047/q050 的"变差"是**与标注约定的分歧**。
→ v2 改为对称分级 `{2,2}`（`evals/build_golden_v2.py`）。

**为什么值得写进报告**：把"精排反而降分"定位到**标注口径**而不是急着调参，是评测可信度的前提——否则会朝错误方向优化。

## 4. 限制与后续（不回避）

| 限制 | 说明 | 建议后续 |
|------|------|---------|
| 召回指标仍饱和 | 68 条中三条主管线 Recall@10 均为 1.0（题目目标是"能召回"） | 增加"应召回但难召回"的负例设计 |
| 精排增益接近噪声 | +0.0098 MRR / −0.0013 nDCG（68 条） | 扩样本（≥300 条）后重测；报告置信区间 |
| 无答案层指标 | Faithfulness / Answer Relevancy 未实测；`groundedness` 是启发式（引用标记覆盖率），**不是 NLI 判分**，两者不可互相冒充 | 引入 RAGAS + judge 独立性设计 + 独立的噪声地板 |
| 语料是仓库文档快照 | golden_v2 的真实语料随仓库演进会"过期"（锚点自检会失败） | 冻结一份语料副本或引入版本化语料仓库 |
| 延迟超预算 | 精排使 P95 从 207ms → 463ms（预算 300ms） | 候选瘦身 / 精排缓存 / 区域就近 |
| 单机单副本 | 所有指标在开发机（Docker Desktop）上测得，未做并发压测 | 需要 QPS/P95 曲线时补压测 |
