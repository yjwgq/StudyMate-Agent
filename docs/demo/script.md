# 3 分钟 Demo 分镜脚本

> 交付物：M10-2 的**可执行部分**（分镜 + 录制清单 + 演示数据准备脚本）。
> 视频由你录制；本文件保证"照着做就能录出一条有说服力的 demo"。
> 目标时长 **3 分钟**，四个场景（对应设计文档 §20 的分镜顺序）。

## 录制前（10 分钟准备）

```powershell
# 1) 起栈并等就绪
docker compose -f infra/docker-compose.dev.yml up -d --build
curl http://localhost:8080/api/v1/ready

# 2) 一键准备演示状态（建用户 / 传语料 / 预置待办 / 打印演示用的三段提问与开关命令）
uv run python scripts/demo_prepare.py

# 3) 清屏（重要）
#    - 关闭无关标签页与聊天软件通知
#    - 浏览器只留 localhost:8080 两个标签：/ 与 /kb/debug
#    - 终端字号调大（16pt+），并 cd 到仓库根目录
```

录屏建议：Windows 用 `Win+G`（Xbox Game Bar）或 OBS；分辨率 1920×1080；麦克风先录 10 秒试听。
**不要在画面里出现的内容**：`.env` 内容、任何 API Key、Langfuse 密钥、个人邮箱（演示用户用 `demo@example.com`）。

## 场景 1：带引用的问答（0:00 – 0:40）

| 项 | 内容 |
|----|------|
| 目标 | 展示"回答有出处、可点开核对" |
| 操作 | 在 `http://localhost:8080` 输入：**「监督学习和无监督学习的区别是什么？」** |
| 预期画面 | 答案逐字流出 → 答案下方出现 `[1] [2]` 引用卡片 → 点开一张，展开显示来源文档、段落号与摘要 |
| 旁白要点 | "答案里的每个事实性论断都带来源编号，点开能看到命中的原文片段；如果模型引不出来源，系统会触发一次重写，仍不达标就在界面标注'缺少资料支撑'。" |

**备用提问**（若知识库为空或检索不到）：先到 `/kb` 上传 `data/evaldocs/ml_basics.md` 并等 `ready`。

## 场景 2：工具调用 + 人工审批（0:40 – 1:30）

| 项 | 内容 |
|----|------|
| 目标 | 展示"危险动作不会自动执行，而是**暂停等人确认**" |
| 操作 | 输入：**「请调用 send_email 工具，给 partner@corp.com 发邮件，主题「合作沟通」，正文「想约下周三讨论合作细节。」」** |
| 预期画面 | ① 出现"工具调用中…" → ② 弹出**审批卡片**（L2 风险、工具名、参数、升级理由"收件人含外部域"）→ ③ 点「批准执行」→ ④ 答案给出执行结果（含邮件 id） |
| 旁白要点 | "风险等级不是模型说了算，是本地策略表；而且支持**参数级升级**——发给内部域是普通写操作，发给外部域自动升到需要人工审批。批准之后它会真的调用工具，可以看到返回的邮件 id。" |

**可选的第二轮（若时间富余）**：再让它发一封外部邮件，这次点「拒绝」→ 展示"模型收到拒绝信号后给出替代回答，而不是卡住或假装成功"。

## 场景 3：中断恢复（1:30 – 2:20）

| 项 | 内容 |
|----|------|
| 目标 | 展示"**进程死了任务照样能继续**"（本 demo 最硬的一段） |
| 操作 | ① 再触发一次外部邮件审批（挂起态）→ ② 切到终端执行 `docker kill personal-agent-os-dev-api-1`，等 3 秒 → ③ `docker compose -f infra/docker-compose.dev.yml up -d api`，等 `/ready` → ④ 回到浏览器**刷新页面**，找到那条待审批的消息 → ⑤ 点「批准执行」 |
| 预期画面 | 刷新后审批卡片仍在（说明状态不在进程内存里）→ 批准后答案正常产出 |
| 旁白要点 | "刚才我把 API 容器 kill 掉了。任务状态在 Postgres 的 checkpoint 里、审批记录在 approvals 表里——所以新进程起来之后，批准这个动作依然能**从断点续跑**，而不是从头再来。" |

**录制技巧**：这段建议不剪辑，一镜到底最有说服力；终端与浏览器同屏（左右分屏）能看到时序。

## 场景 4：降级角标（2:20 – 3:00）

| 项 | 内容 |
|----|------|
| 目标 | 展示"依赖挂了系统还能用，**而且用户知道自己在看降级结果**" |
| 操作 | ① 终端执行 `curl -X POST http://127.0.0.1:8080/api/v1/flags -H "Content-Type: application/json" -d '{"name":"retrieval.rerank.enabled","value":false}'` → ② 回浏览器提问「什么是交叉验证？」→ ③ 展示角标后，再关掉向量路：把 `retrieval.vector.enabled` 设为 false → ④ 再问一次，展示"未走向量检索" |
| 预期画面 | 答案正常产出 + 角标：「⚠ 未精排（排序质量下降）」→「⚠ 未走向量检索」；可顺带切到 `/kb/debug` 看**逐路分数**（向量路 0 条 / 关键词路 28 条）与生效开关 |
| 旁白要点 | "精排关了、向量检索关了，系统都还在工作——但它**不会偷偷降级**：页面明确告诉你哪一环降级了、影响是什么。这比'高可用'更能体现产品意识。" |
| 收尾 | 恢复开关：把两个 flag 都设回 `null`（清除覆写） |

## 需要展示但**没有**数字的地方（避免被抓）

- 不要说"准确率提升 X%"——本项目**没有答案层指标**（Faithfulness 等未实测，见 `docs/eval_report.md` 的限制章）。
- 可说"检索层 nDCG@10 从 0.9497 提升到 0.9567、MRR 从 0.9240 到 0.9485"，这些数字都能在 `evals/reports/m7_scores.json` 里查到。
- 视频里如果被问到成本，如实说"没有做成本聚合，只有原始 token 用量"。
